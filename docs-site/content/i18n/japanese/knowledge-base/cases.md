# 知識ベースの応用例

知識ベースの信頼性は、資料の量ではなく、境界が明確であるか、出典が保守可能であるか、実際の質問に対して正しく証拠を安定して検索できるかに依存します。

{% hint style="info" %}
以下のパラメータは出発点としてのみ使用してください。まず代表的な資料 3〜10 件でインポート、検索、利用の流れを確立し、その後、固定された質問セットに基づいて拡張してください。
{% endhint %}

## まず同じ方法で設計する

{% stepper %}
{% step %}
### 1. 最終的なタスクを明確にする

ユーザーが行う判断や成果物（例：制度の照会、障害の調査、研究レポートの作成など）を明確に定義します。
{% endstep %}

{% step %}
### 2. 資料の範囲を定義する

同じ知識ベースに配置するのは、利用時に一緒に検索されるべき資料のみです。権限、ライフサイクル、製品モデル、バージョンが異なるコンテンツは、優先的に分離してください。
{% endstep %}

{% step %}
### 3. 出典と更新方法を選択する

マニュアル、ノート、目次、ウェブページは誰が管理し、いつ差し替え、履歴バージョンの保持が必要かを確認します。
{% endstep %}

{% step %}
### 4. 検収質問を用意する

正確な事実、条件付きルール、口語的な質問、混同しやすいバージョンをカバーする、実際の質問 3〜10 件を用意します。
{% endstep %}

{% step %}
### 5. 検索戦略を調整する

まずシンプルな設定を維持します。BM25 では同義表現の処理が不十分な場合に埋め込みを追加し、候補は正しいが順序が不安定な場合にリランキングを追加します。
{% endstep %}

{% step %}
### 6. 対話または Agent に接続する

単一の質問応答には通常の対話を使用します。多段階の研究、比較、ファイルの納品が必要な場合は Agent にバインドします。リリース前に出典を1件ずつ確認してください。
{% endstep %}
{% endstepper %}

## ユーザーケース 1：社内制度の Q&A

### 目標

従業員が出張承認、宿泊基準、経費精算の例外を照会でき、出典を開いて原文を確認できるようにします。

### 資料の構成

* 知識ベース：【従業員出張制度】
* エントリ：【出張承認フロー】
* エントリ：【宿泊基準早見表】
* エントリ：【出張に関するよくある質問】

<figure><img src="../../../assets/2414cfc005a860f127a4fd96.webp" alt="知識ベースの応用例 — 説明画像"><figcaption><p>制度条項と FAQ は分離して管理し、一方を更新する際に全資料の再作成を避けます。</p></figcaption></figure>

### 推奨設定

| 項目 | 出発点 | 調整タイミング |
| ---- | ---------- | ----------------- |
| 検索 | まず BM25 を使用 | 従業員の質問と制度の表現に大きな差異がある場合に埋め込みを追加 |
| リランキング | まず使用しない | 正しい候補が表示されるが順序が不安定な場合に有効化 |
| 資料バージョン | 現行版のみ保持 | 履歴監査で並存が必要な場合、名称に年号を記載 |
| 回答要件 | 結論、条件、出典を分離 | 資料に明記がない場合は明確にマーク |

### 検収質問

1. 出張時のホテル代は最大いくらまで経費精算できますか？
2. 海外でのレンタカー代は経費精算できますか？
3. 総費用が 5,000 元を超える場合、誰が承認しますか？
4. 承認なしにホテルを予約した場合、どのように処理されますか？

### 対話プロンプト

> 「従業員出張制度」に基づいてのみ回答してください。まず結論を述べ、次に適用条件と出典を列挙します。資料に明記がない場合は「制度に明記なし」と記載し、常識で補完しないでください。

{% hint style="success" %}
検収合格の基準は、同じ制度について原文の表現と口語的な表現の両方でヒットし、回答内の金額、役割、条件が引用によって直接裏付けられることです。
{% endhint %}

## ユーザーケース 2：製品アフターサービスアシスタント

### 目標

公式マニュアル、障害コード、審査済みケースを整理し、カスタマーサポートが安全で追跡可能なトラブルシューティング提案を優先的に提供できるようにします。

### 資料の境界

| 知識ベースまたは資料グループ | 内容 | 管理原則 |
| ------- | ------------- | ------------- |
| 公式マニュアル | 仕様、保証範囲、標準手順 | モデルと文書バージョンを保持 |
| 障害コード | 1つの障害ごとに 1 セクション | 適用ファームウェアとデバイスモデルを明記 |
| 審査済みケース | 原因と解決策が確認されたケース | 未審査のチャットログは直接インポートしない |

モデル間のルールに顕著な差異がある場合は、モデルごとに独立した知識ベースに分割し、同じ障害コードの競合を避けてください。

### 検索と Agent の設定

* PDF はまず目次、表、2 段組本文を抜き出して確認します。
* 障害コードは正確な用語に依存するため、BM25 を維持します。
* 顧客の説明が口語的な場合は、埋め込みモデルを追加します。
* アフターサービス Agent には公式マニュアルと審査済みケースをバインドし、【知識ベース検索】のみを有効にします。

> デバイスモデル、障害コード、症状に基づいて 3 ステップで調査してください。各ステップで、根拠が公式マニュアルか審査済みケースかを明記します。分解、電気的使用、データ消去に関わる場合は、まずリスクを警告し、確認を待ってください。

### 検収基準

* 他のモデルの手順を現在のモデルに適用しない。
* 安全警告が操作手順の前に表示される。
* 公式ルールとケースの提案を分離する。
* 資料の裏付けがない場合は人間にエスカレーションし、推測しない。

## ユーザーケース 3：研究資料とレポート

### 目標

論文、インタビューノート、ウェブスナップショットから検証可能な証拠を抽出し、Agent が出典付きの比較レポートを生成します。

### 資料の構成

* 研究課題ごとに知識ベースを作成し、すべての論文を 1 つの大きな知識ベースに詰め込まない。
* ファイル名に著者、年、短いタイトルを含める。
* インタビューノートには、インタビュー対象者の役割、日付、引用可否を明記する。
* ウェブ資料は取得日付を記録する。知識ベースにはインポート時のスナップショットが保存されるため。

<figure><img src="../../../assets/8cd27fa50051cc96320b280a.webp" alt="知識ベースの応用例 — 説明画像"><figcaption><p>研究用知識ベースは、まず固定された質問で出典のカバレッジを検証し、その後 Agent にドキュメント横断の要約を依頼します。</p></figcaption></figure>

### Agent プロンプト

> バインドされた研究知識ベースから「ユーザーが初期設定を放棄する理由」に関する証拠を検索してください。まず出典ごとに元の意見と制約を列挙し、次にコンセンサス、相違点、検証待ちの仮説を要約します。最終的に Markdown レポートを生成します。推測をインタビュー対象者の発言として記載しないでください。

### 証拠から成果物へ

<figure><img src="../../../assets/31b376b5d5a233eeb71ddf12.webp" alt="知識ベースの応用例 — 説明画像"><figcaption><p>まず証拠と制約を保持し、その後 Agent にレポートへの整理を依頼します。完成品が元の出典を隠蔽しないようにしてください。</p></figcaption></figure>

### 検収基準

* コンセンサスは少なくとも 2 つの独立した出典によって裏付けられる。
* 相違点はそれぞれの条件を保持し、無理に統合しない。
* 引用、推論、提案に明確な識別子がある。
* ウェブスナップショットと論文のバージョンが追跡可能である。

## 設定説明：再利用可能な設計表

| 項目 | 回答すべき質問 |
| ---- | ---------------------- |
| 目標 | ユーザーは最終的にどのような判断を行い、どのような成果物を納品しますか？ |
| 境界 | どの資料を一緒に検索し、どの資料を分離すべきですか？ |
| 出典 | ファイル、ノート、目次、ウェブページはどのように更新しますか？ |
| 解析 | どのタイプの文書で OCR、表、順序の問題が発生しやすいですか？ |
| 検索 | BM25 は十分ですか？いつ埋め込みとリランキングが必要ですか？ |
| 検収質問 | 実際の使用を代表する 3〜10 件の質問はどれですか？ |
| 失敗処理 | 結果なし、バージョン競合、資料の裏付けがない場合はどうしますか？ |
| 管理 | 誰が資料の差し替え、再インデックス作成、バックアップを担当しますか？ |

{% hint style="warning" %}
「多くの資料をインポートした」ことを完了の基準にしないでください。資料が増えるほど、重複バージョン、権限の混在、ノイズの競合を明示的に管理する必要があります。
{% endhint %}

## よくある質問

<details>

<summary>制度、マニュアル、ケースは同じ知識ベースに置くべきですか？</summary>

同じ質問で一緒に検索されるべきか、権限と更新サイクルが一致するかを確認してください。差異が顕著な場合は、知識ベースを分割することで出典の境界をより制御しやすくなります。

</details>

<details>

<summary>ケースベースにカスタマーサポートのチャットをすべて直接インポートできますか？</summary>

推奨しません。まず原因、解決策、プライバシー内容を審査し、確認済みで再利用可能なケースのみをインポートしてください。

</details>

<details>

<summary>資料を拡張する前に何をすべきですか？</summary>

固定された検収質問セットを保持し、バッチごとにインポートして再テストしてください。新しい資料が結果を劣化させた場合、どのバッチの内容が原因かを迅速に特定できます。

</details>
