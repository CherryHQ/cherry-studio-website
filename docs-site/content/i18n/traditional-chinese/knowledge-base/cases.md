# 知識庫應用案例

知識庫是否可靠，不取決於資資數量，而取決於邊界是否清楚、來源是否可維護，以及真實問題能否穩定召回正確證據。

{% hint style="info" %}
下面的參數只作為起點。先用 3～10 份代表性資資跑通匯入、召回和使用，再根據固定問題集擴充。
{% endhint %}

## 先用同一套方法設計

{% stepper %}
{% step %}
### 1. 寫清最終任務

明確使用者要做的判斷或交付物，例如查詢制度、排查故障或生成研究報告。
{% endstep %}

{% step %}
### 2. 劃定資資邊界

只有使用時應該一起檢索的資資才放在同一知識庫。權限、生命週期、產品型號或版本不同的內容優先分開。
{% endstep %}

{% step %}
### 3. 選擇來源和更新方式

說明文件、筆記、目錄和網頁由誰維護，何時替換，是否需要保留歷史版本。
{% endstep %}

{% step %}
### 4. 準備驗收問題

準備 3～10 個真實問題，覆蓋精確事實、條件規則、口語問法和容易混淆的版本。
{% endstep %}

{% step %}
### 5. 調整檢索方案

先保留簡單配置。BM25 不足以處理同義表達時再加嵌入；候選正確但順序不穩時再加重排。
{% endstep %}

{% step %}
### 6. 接入對話或 Agent

一次問答使用普通對話；需要多步研究、比較和檔案交付時綁定 Agent。上線前逐條核對來源。
{% endstep %}
{% endstepper %}

## 使用者案例一：員工制度問答

### 目標

讓員工查詢差旅審批、住宿標準和報銷例外，並能打開來源核對原文。

### 資資組織

* 知識庫：【員工差旅制度】
* 條目：【出差審批流程】
* 條目：【住宿標準速查】
* 條目：【差旅常見問題】

<figure><img src="../../../assets/2414cfc005a860f127a4fd96.webp" alt="知識庫應用案例 — 說明圖片"><figcaption><p>制度條款和 FAQ 分開維護，更新其中一份時不必重做全部資資。</p></figcaption></figure>

### 推薦配置

| 項目 | 起點 | 何時調整 |
| ---- | ---------- | ----------------- |
| 檢索 | 先用 BM25 | 員工問法與制度措辭差異大時增加嵌入 |
| 重排 | 先不使用 | 正確候選已出現但順序不穩定時啟用 |
| 資資版本 | 只保留當前版 | 歷史稽核需要並存時在名稱中寫明年份 |
| 回答要求 | 結論、條件、來源分開 | 資資未說明時明確標記 |

### 驗收問題

1. 出差住店最高能報多少？
2. 海外租車能否報銷？
3. 預計總費用超過 5000 元時由誰審批？
4. 未經批准先訂酒店會怎樣處理？

### 對話提示詞

> 只根據「員工差旅制度」回答。先給結論，再列適用條件和來源；資資沒有說明時寫「制度未說明」，不要用常識補全。

{% hint style="success" %}
驗收通過時，同一條制度用原文問法和口語問法都能命中，回答中的金額、角色和條件可以由引用直接支持。
{% endhint %}

## 使用者案例二：產品售後助手

### 目標

把官方手冊、故障代碼和已審核案例組織起來，讓客服先給安全、可追溯的排查建議。

### 資資邊界

| 知識庫或資資組 | 內容 | 維護原則 |
| ------- | ------------- | ------------- |
| 官方手冊 | 規格、保固邊界、標準步驟 | 保留型號和文件版本 |
| 故障代碼 | 一條故障一個小節 | 標註適用韌體和設備型號 |
| 審核案例 | 已確認原因與解決方案案例 | 未審核聊天記錄不得直接匯入 |

不同型號規則差異明顯時，按型號拆成獨立知識庫，避免相同故障碼互相競爭。

### 檢索與 Agent 配置

* PDF 先抽查目錄、表格和雙欄正文。
* 故障碼依賴精確術語，保留 BM25。
* 客戶描述較口語化時增加嵌入模型。
* 給售後 Agent 綁定官方手冊和審核案例，只啟用【知識庫搜尋】。

> 根據設備型號、故障碼和現象分三步排查。每一步標明依據來自官方手冊還是審核案例。涉及拆機、用電或資資清除時，先提示風險並等待確認。

### 驗收標準

* 不把其他型號的步驟用於當前型號。
* 安全警告出現在操作步驟之前。
* 官方規則和案例建議分開。
* 無資資支持時轉人工，不猜測。

## 使用者案例三：研究資資與報告

### 目標

從論文、訪談筆記和網頁快照中提取可核對證據，再由 Agent 生成帶來源的比較報告。

### 資資組織

* 按研究問題建庫，不把全部論文塞進一個大庫。
* 檔案名稱包含作者、年份和短標題。
* 訪談筆記標明受訪者角色、日期和是否可引用。
* 網頁資資記錄抓取日期，因為知識庫保存的是匯入快照。

<figure><img src="../../../assets/8cd27fa50051cc96320b280a.webp" alt="知識庫應用案例 — 說明圖片"><figcaption><p>研究庫先用固定問題驗證來源覆蓋，再交給 Agent 做跨文件歸納。</p></figcaption></figure>

### Agent 提示詞

> 在已綁定研究知識庫中查找「使用者為何放棄首次配置」的證據。先按來源列出原始觀點和限制，再歸納共識、分歧和待驗證假設。最終生成 Markdown 報告；不得把推斷寫成受訪者原話。

### 從證據到交付物

<figure><img src="../../../assets/31b376b5d5a233eeb71ddf12.webp" alt="知識庫應用案例 — 說明圖片"><figcaption><p>先保留證據和限制，再讓 Agent 整理為報告；不要讓成品反過來掩蓋原始來源。</p></figcaption></figure>

### 驗收標準

* 共識由至少兩個獨立來源支持。
* 分歧保留各自條件，不強行合併。
* 引用、推斷和建議有明確標識。
* 網頁快照和論文版本可追溯。

## 配置說明：可重用設計表

| 項目 | 要回答的問題 |
| ---- | ---------------------- |
| 目標 | 使用者最終要做出什麼判斷或交付什麼結果？ |
| 邊界 | 哪些資資應該一起檢索，哪些必須分開？ |
| 來源 | 檔案、筆記、目錄和網頁怎樣更新？ |
| 解析 | 哪類文件最容易出現 OCR、表格或順序問題？ |
| 檢索 | BM25 是否足夠？何時需要嵌入和重排？ |
| 驗收問題 | 哪 3～10 個問題代表真實使用？ |
| 失敗處理 | 無結果、衝突版本和無資資支持時怎麼辦？ |
| 維護 | 誰負責替換資資、重新索引和備份？ |

{% hint style="warning" %}
不要把「匯入了很多資資」當成完成標準。資資越多，重複版本、權限混合和噪聲競爭越需要被顯式管理。
{% endhint %}

## 常見問題

<details>

<summary>制度、手冊和案例應該放在同一個知識庫嗎？</summary>

看它們是否應該在同一問題中共同檢索，以及權限和更新週期是否一致。差異明顯時拆庫更容易控制來源邊界。

</details>

<details>

<summary>案例庫可以直接匯入全部客服聊天嗎？</summary>

不建議。先審核原因、解決方案和隱私內容，只匯入已確認、可重用的案例。

</details>

<details>

<summary>擴充資資前需要做什麼？</summary>

保留一組固定驗收問題，分批匯入並複測。新增資資讓結果退化時，能快速定位是哪一批內容造成的。

</details>
