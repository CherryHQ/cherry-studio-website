# 長對話、上下文與排隊訊息

對話越長，模型需要閱讀的歷史越多。當上下文用量接近上限時，較早的內容可能無法繼續參與回答。與其不斷追加一句「繼續」，不如定期整理結論和未決問題。

### 管理長對話

{% stepper %}
{% step %}
#### 1. 觀察上下文提示

當介面提示上下文壓力變大時，先停止添加大型附件，檢查哪些歷史仍然與目前目標有關。
{% endstep %}

{% step %}
#### 2. 讓模型生成交接摘要

要求它分開列出「已確認事實、目前結論、待解決問題、不能遺失的限制」。這比普通的「總結一下」更適合繼續工作。
{% endstep %}

{% step %}
#### 3. 新開話題繼續

把交接摘要和必要檔案放入新話題，第一則訊息說明接下來只處理哪個目標。原話題保留作參考。
{% endstep %}
{% endstepper %}

### 調整全域上下文管理

路徑：【設定】→【一般】→【上下文管理】。這些設定適用於一般助手對話；單一助手還可以在自身設定中覆蓋。

| 設定項目 | 產品預設值 | 建議起點 | 作用 | 適用情境 | 注意事項 |
| -------- | -------- | ------- | ------------- | ------------- | --------------- |
| 保留最近訊息數 | 不限制 | 先不限制 | 只把最近若干則訊息送給模型 | 固定窗口的短任務 | 過小會讓模型忘記仍有效的要求 |
| 啟用上下文管理 | 開啟 | 保持開啟 | 管理超長工具結果和歷史壓縮 | 長對話、工具呼叫多的任務 | 關閉後大結果更容易擠滿上下文 |
| 工具輸出截斷閾值 | 50000 字元 | 保持預設 | 大結果轉存後讓模型分段讀取 | 網頁、日誌、長文件工具結果 | 不等於刪除原始結果 |
| 自動壓縮 | 開啟 | 保持開啟 | 接近窗口上限時總結較早歷史 | 持續多輪工作 | 壓縮是摘要，不保證保留每個細節 |
| 壓縮模型 | 跟隨目前模型 | 先跟隨目前模型 | 選擇生成歷史摘要的模型 | 需要單獨控制速度或成本 | 更換模型會增加排錯變數 |

【設定】→【預設模型】還提供【模型呼叫重試】。預設關閉；開啟後預設最多嘗試 3 次並使用指數退避，還可以按順序選擇回退模型。重試和回退只在模型開始輸出前生效，不會把已經生成一半的回答改用另一個模型繼續。

### 使用訊息佇列

模型仍在回覆時，可以把下一則要求加入佇列。適合追加一個明確的後續動作，例如「完成後再整理成三條結論」。Agent 執行中若要立即糾正目前方向，使用【引導快捷鍵】；如果需要徹底重來，再停止目前生成並重新說明目標。

<figure><img src="../../../../assets/a62a413bccd43d18b59ee293.webp" alt="長對話、上下文與排隊訊息 — 說明圖片"><figcaption><p>暫停時可以先核對結果；恢復後，排隊訊息會按照從上到下的順序繼續發送。</p></figcaption></figure>

圖中：① 目前話題中兩則排隊訊息；② 恢復自動發送。恢復後，訊息會按照從上到下的順序繼續發送。

{% hint style="info" %}
佇列不是自動化計畫。它只負責目前話題裡的後續訊息；需要在固定時間執行，請使用【排程任務】。
{% endhint %}

#### 應用案例：審閱一份長報告

先上傳報告並要求按章節列出問題。模型處理時，把「完成後整理風險清單」和「最後生成檢查表」依次加入佇列。需要先核對第一輪結果時，可以暫停自動發送；確認無誤後再恢復。這樣不用守在對話前逐則發送，也能避免下一步要求搶在核對之前執行。

<summary>為什麼模型突然忘了前面說過的要求？</summary>
